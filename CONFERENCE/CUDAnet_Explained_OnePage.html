60-second summary

CUDAnet is a neural network trainer written by hand in CUDA — no PyTorch, no TensorFlow. Training a network on a GPU means splitting the work across thousands of tiny parallel workers called threads. That's safe for most of the math — but two popular training algorithms, Momentum and Adam, keep a running memory that every thread wants to update at once. Update it naively, and thousands of threads silently overwrite each other's work — accuracy collapses to 0%, with no error message at all.

The fix — Two-Phase Gradient Accumulation (2PGA) — splits every update into two steps: first let all threads safely add up their contributions (safe, because addition doesn't care about order), then let exactly one thread per weight apply the real update (safe, because nobody else is touching that memory at the same time). That one change takes accuracy from 0% back to 97.2%, at a cost of under half a percent of runtime.

01 — The Problem

Why parallel training has a blind spot

A GPU trains a network by giving each image in a batch to its own thread. Every thread runs the network forward, sees how wrong its prediction was, and works out how each weight should change. As long as every thread's work stays separate, this is perfectly safe — thousands of threads can run at the exact same instant with no conflict at all.

GPU
→
2,048 threads
→
shared memory
Every thread wants to update the SAME optimizer memory at the SAME instant — nothing enforces an order.

The trouble starts at the update step. Plain gradient descent (SGD) has no memory between steps — every update stands alone. But Momentum and Adam are built to remember: Momentum keeps a running "velocity," Adam keeps two running "moment" estimates. All 2,048 threads want to read, update, and write back that same shared memory at once. Whichever thread writes last simply erases what every other thread just did — silently, with no crash and no warning.

What actually happens if you don't fix this

Momentum's accuracy collapses from 97.2% to 0.0% — indistinguishable from a network that was never trained. Adam does the same. Both fail this way because atomicAdd, the one safety tool CUDA gives you, only protects a single addition — not the full "read, multiply, add, write back" recipe that Momentum and Adam actually need.

Why this bug hides so well

  • The code compiles and runs without any error — races don't throw exceptions.
  • SGD, which has no memory to corrupt, keeps working fine — so testing SGD first looks like proof the whole approach is sound.
  • Frameworks like PyTorch never let you write the buggy version in the first place — the optimizer step is always a separate call from the backward pass, so this failure mode is invisible to anyone who has only ever trained through a framework.
02 — The Fix

Two-Phase Gradient Accumulation (2PGA)

The fix doesn't add locks or exotic hardware tricks. It changes who is allowed to touch what memory, at two separate moments in the same batch.

PHASE 1
2,048 threads
atomicAdd only
→
SYNC
→
PHASE 2
1 thread per weight
full formula, no race
Phase 1 only ever sums numbers — safe, because addition doesn't care about order.
Phase 2 gives each weight exactly one owner — safe, because there's no one left to race against.
// Phase 1 — many threads, safe because "+" is commutative
atomicAdd(&grad_w[i], sample_gradient);

// barrier — wait until EVERY thread has finished Phase 1
cudaDeviceSynchronize();

// Phase 2 — ONE thread owns EACH weight; nobody else can touch it
g = grad_w[i] / batch_size;      // average the batch
v = beta * v + g;                 // the real Momentum/Adam formula
theta[i] -= lr * v;               // applied exactly once

This isn't "slower mini-batch SGD in disguise." Phase 1 was already producing the correct summed gradient before this fix existed — nothing changes there. The entire fix lives in Phase 2 alone: give every weight exactly one thread that's allowed to touch it, and the race disappears by construction, not by locking or waiting it out.

Cost of the fix

For the 128×128 network in this project, Phase 2 touches about 18,000 weights and finishes in under 0.01 milliseconds — under 0.5% of one epoch's time. The idea scales to any number of parameters: assign one thread per weight, across as many blocks as needed, and "exactly one owner per address" stays true no matter how large the model gets.

The evidence, in the actual source code

The codebase still contains two functions — update_param_momentum and update_param_adam — that implement the old, broken approach. They're defined but never called from anywhere; they're the fossil record of the exact bug this fix resolves. Reading them side by side with the real, working apply_optimizer_update kernel is the clearest way to see the difference between "one atomic call that looks safe" and "actually safe."

  • Optional Batch Normalization after every hidden linear layer.
  • Every weight and bias lives in one flat array on the GPU — no objects, no pointers, just precomputed offsets. A weight's address is one multiply-add away, which is exactly what a GPU's memory system prefers.
  • The whole network shape (layer sizes, memory offsets) is described by one small struct that gets passed into every kernel — cheap enough to pass by value rather than by pointer.
04 — Mechanics

How one training step actually runs on the GPU

The five stages

Every stage is one or more GPU kernels. "Update" is where 2PGA lives.

Forward pass

Each thread copies its own image into an activation buffer, then for every layer computes z = W·a + b, applies ReLU (hidden layers) or softmax (output layer). Softmax subtracts the largest value before exponentiating — a standard trick to stop very large numbers from overflowing.

Backward pass

Because the output uses softmax + cross-entropy, the output error has an unusually clean form: δ = prediction − true_label. Every earlier layer's error is found by pushing that signal back through the transpose of the weight matrix, masked by the ReLU derivative — a plain 0-or-1 gate depending on whether the forward-pass value was positive.

Memory layout

The dataset dominates the footprint — and because it's uploaded once and stays resident in VRAM, the GPU never re-reads it from scratch the way a CPU implementation re-reads it every epoch. That's a real part of why the GPU numbers look so favorable, not just raw compute speed.

Threads, blocks, and why the race condition is even possible

Threads are grouped into small teams called blocks (128 or 256 threads each here). Threads inside one block can synchronize with each other; blocks cannot synchronize with other blocks in the middle of a kernel. With 2,048 threads split across 16 blocks, there is no built-in way for one block to know what another block is doing at any given instant — which is exactly the condition a race condition needs to exist.

05 — The Optimizers

SGD, Momentum, and Adam — how each one behaves under the hood

SGD — the one that was never broken

θ ← θ − η·g. No memory between steps, so there's nothing for two threads to race over. Summing gradients is commutative — atomicAdd alone is already completely correct. This is exactly why the bug is easy to miss: test SGD first, and everything looks fine.

Momentum — fails without the fix

v ← βv + g, then θ ← θ − ηv. That v is a single shared number that every thread wants to read, update, and write back. Two threads reading the same old v and racing to write their own version back means one of them always loses — permanently, not just delayed.

Without 2PGA

97.2% → 0.0%

Adam — the same failure, twice over

Adam keeps two running estimates instead of one: m (a moving average of the gradient) and v (a moving average of the squared gradient). The identical race happens on both simultaneously.

m = β₁m + (1−β₁)g  ·  v = β₂v + (1−β₂)g²  ·  θ ← θ − η·m̂/(√v̂ + ε)
Without 2PGA

97.2% → 0.0% — identical failure signature to Momentum

A real, subtle detail worth knowing

Adam's bias-correction step counter is supposed to increase once every mini-batch. In this codebase it currently increases once per epoch instead — so across 20 epochs of 23 mini-batches each, it only ever reaches 20, not 460. This doesn't touch the race-condition story at all (it's just bookkeeping), but it's a genuine, checkable detail if anyone asks about it closely.

06 — Batch Normalization

Why batch norm needs its own GPU strategy

Batch normalization re-centers every neuron's values using the mean and variance across the whole batch. That's the catch: computing a mean needs every one of 2,048 samples' values already sitting in memory — but a single kernel launch can't guarantee that, since different thread blocks run in no particular order relative to each other.

linear
→
sync
→
stats
→
apply
→
activate
Same synchronization principle as 2PGA — a hard barrier before anyone reads a value that depends on the whole batch.
μ = mean(z)  ·  σ² = variance(z)  ·  ẑ = (z − μ)/√(σ²+ε)  ·  output = γẑ + β

The fix is a staged pipeline of small kernels, each one finishing completely before the next begins: compute the linear layer, synchronize, compute batch statistics with a parallel reduction, apply the normalization, then activate. The same shape repeats going backward.

An older, unused implementation still exists

The source also contains an earlier batch-norm implementation (batch_norm_forward, batch_norm_backward) that has exactly the race-prone shape this section describes fixing. It still compiles, but the actual training loop never calls it — it was superseded by the staged pipeline above and left in place as an artifact of the project's history.

07 — Learning Rate

Learning rate scheduling

Three schedules are supported — step decay, exponential decay, and cosine annealing — chosen at compile time. One implementation choice mattered more than expected: whether the schedule counts by epoch or by mini-batch step.

What went wrong the first time

Indexing by epoch instead of by step compresses the entire decay curve into 23 times fewer steps than intended (since there are 23 mini-batches per epoch here) — the learning rate collapses toward zero long before the network has actually converged. Indexing by the true global step fixes it.

Momentum and Adam land in a statistical tie at 97.2%, both meaningfully ahead of plain SGD. They also converge fast — within 5 of the 20 epochs, both are already within about a point of their final accuracy.

The one result that doesn't behave — and why that's worth saying out loud

BN + Adam + LR peaks early at 88.1% around epoch 2, then declines steadily to 81.0% by epoch 20. A curve that rises then falls is the signature of instability, not slow convergence — something is actively getting worse, not just improving slowly. Swapping the per-batch cosine schedule for a per-epoch exponential one only recovered about a point, which rules out the schedule as the main cause. The leading hypothesis is a genuine tug-of-war between Adam's evolving moment estimates and batch norm's evolving statistics — two different kinds of "memory" pulling against each other. It's reported openly as unresolved, not smoothed over.

Speed

A serial CPU baseline takes roughly 2,070 seconds per epoch (measured, not just estimated). Every CUDA configuration finishes in about one second — SGD's 0.94 seconds is a 2,202× speedup, and even the heaviest configuration still holds 1,669×.

09 — Glossary

Every term, simply first, then technically

Thread

One tiny independent worker on the GPU — usually handling one training image here.

The smallest unit of execution on a GPU: its own registers and program counter, one of thousands launched to run identical code over different data.

Kernel

The one small program every thread runs at the same time.

A __global__ function launched from the host with a specified thread count, executed identically but on different data by every thread.

Block / Grid

Threads are grouped into small teams (blocks); all the blocks together are the grid — like a stadium organized into sections.

A block (128–256 threads here) can synchronize internally and share fast on-chip memory; blocks cannot synchronize with each other mid-kernel — the root structural reason the race condition is possible.

Race condition

Two workers update the same shared notebook at once; whoever writes last erases the other's update, silently.

Undefined behavior when two-plus threads access the same memory concurrently with at least one write and no enforced ordering.

atomicAdd / atomic operation

One action guaranteed to happen all at once — nobody can interrupt it halfway.

A hardware-guaranteed indivisible read-modify-write. It only protects that single operation — a multi-step formula built around it is not automatically made safe.

Synchronization barrier (cudaDeviceSynchronize)

A checkpoint: make everyone finish the current task before anyone starts the next.

A host-side call that blocks until every previously launched kernel has fully completed — the reliable way to guarantee visibility of all writes before a dependent kernel reads them.

Batch normalization

Re-centers a layer's values using the batch's own average and spread, then lets the network re-scale/re-shift as it prefers.

Normalizes pre-activations per feature over the mini-batch (μ, σ²), then applies a learned affine transform (γ, β).

Throughput / speedup

How much work gets done per second, and how many times faster that is than the slow way.

Speedup = Tbaseline / Taccelerated, measured via CUDA event timers against a serial CPU implementation of the same algorithm.

10 — Questions People Ask

The questions that come up, answered

Why doesn't atomicAdd already fix the race condition?

Because it only makes one addition indivisible. Momentum's update is "read the old velocity, multiply, add, write back" — several steps. An atomic protects one step, not the whole sequence.

Does this bug affect anything besides Momentum and Adam?

Any optimizer with state that carries across steps — RMSProp, LAMB, Adagrad — has the identical failure mode and the identical fix. SGD is the one clean exception, since it has no such state.

Isn't this the same thing frameworks already do?

Structurally, yes — optimizer.step() is always separate from backward(). The contribution here is making that separation explicit and proving, with real before/after numbers, exactly what breaks if you skip it.

Why does the barrier (cudaDeviceSynchronize) matter if kernels on the same stream already run in order?

In this specific single-stream program, default ordering already guarantees it — the explicit barrier is best understood as defensive, unambiguous correctness, and it's what genuinely matters for the Phase 1 → Phase 2 boundary and for accurate timing/evaluation.

Why is the full-feature build (BN + Adam + LR) the worst-performing configuration?

Because the actual contribution is the two-phase mechanism, not any one configuration being "the best." Reporting the BN+Adam interaction honestly is what makes the other numbers trustworthy.

Is the WMMA / Tensor Core build actually using Tensor Cores?

Not currently — the real WMMA kernels exist in the source and are architecturally correct, but a preprocessor flag issue keeps them from being compiled into the default build. It's an honest gap, not a claim made anywhere in the paper.

11 — Contributions & Limits

What this project actually contributes — and where it falls short

Contributions

  • Two-Phase Gradient Accumulation — a general, lock-free fix for any stateful optimizer parallelized on a GPU.
  • A correct, synchronized CUDA implementation of Batch Normalization.
  • A < 2 MB, dependency-free training engine, benchmarked directly against PyTorch.
  • An empirical, reproducible before/after demonstration — not just a theoretical argument.

Limitations

  • MLP accuracy (97.2%) trails CNN-level results (>99%) — a deliberate scope choice, not an oversight.
  • BN + Adam + LR's instability is real and not yet fully explained.
  • Single GPU, single seed — the qualitative result (0%→97%) is robust; absolute numbers are not claimed to generalize across hardware.
  • Phase 2's synchronization overhead grows with batch size — about +17% epoch time at 4,096 vs. 2,048.

Future work

  • Wire up the already-implemented Tensor Core (WMMA) kernels for a further 2–3× throughput.
  • Add convolutional layers via im2col to push past MNIST toward CIFAR-10.
  • Scale to multiple GPUs via NCCL AllReduce — requires no change to the core 2PGA argument.
