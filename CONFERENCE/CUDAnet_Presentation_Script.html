How to present CUDAnet like you've given this talk fifty times

Read this part first — how to use the guide

You did not just write a summary of someone else's work. You found and fixed a real, reproducible bug. Every time you feel nervous in the next ten minutes, remember that one fact: you can reproduce 0.0% accuracy on command, and you can reproduce 97.2% on command, by changing one thing. That's a stronger position than most people walk into a conference room with.

Each slide below has the same eight parts, always in this order: what's on the slide, what you say (word for word — read it a few times until it sounds like you, not like a script), why the slide exists in the talk's argument, the figures to display, any code you're allowed to show, keywords to land with emphasis, what to physically point at, and the questions people are likely to ask with your best answer ready. A final "mistakes to avoid" list closes each slide.

Timing: the full script below runs about 12 minutes 25 seconds read at a natural, unhurried pace. If your slot is a hard 10, cut Slide 3 (Related Work) down to naming two papers instead of four, and read Slide 8 (Experimental Setup) faster — those two cuts alone save about a minute and a half without touching your actual contribution.

CUDA words you need to own before you say them out loud

You don't need to be a CUDA expert to give this talk well — you need to be able to define eight words without hesitating, because the moment you hesitate on a word like "kernel" or "atomic," the audience stops trusting the rest of the talk. Read this once, out loud, the night before.

GPU vs. CPU

A CPU is a handful of very smart workers who can each do complicated things one after another, fast. A GPU is thousands of much simpler workers who can each only do one simple thing — but they all do it at the exact same instant.

A CPU has a few (4–64) powerful cores optimized for low-latency sequential instruction streams; a GPU has thousands of simpler cores (3,328 on the RTX A2000 used in this paper) optimized for high-throughput data-parallel execution of the same instruction across many data elements — exactly the shape of "run this same forward pass on every image in the batch."

Thread

One single worker. In this paper, one thread usually handles one training image.

The smallest unit of execution on a GPU — a single instruction stream with its own registers and program counter, one of thousands launched together to run identical code over different data.

Kernel

The one small program that every thread runs. You write it once; the GPU runs thousands of copies of it at the same time.

A function marked __global__ in CUDA C, launched from the CPU with a specified number of threads, executed identically (but on different data) by every one of them.

Block & grid

Threads are organized into small teams called blocks, and all the blocks together are called a grid — like a stadium organized into sections, and the sections together make the whole crowd.

A block is a group of threads (this paper uses 128 or 256 per block) that can synchronize with each other and share fast on-chip memory; a grid is the full set of blocks launched by one kernel call. Blocks cannot synchronize with each other mid-kernel — this fact is exactly why the race condition in this paper is possible.

Race condition

Two workers try to update the same shared notebook at the same time. Both read "100," both add their own number, both write back — whoever writes last erases the other's contribution, and nobody notices.

Undefined behavior arising when two or more threads access the same memory location concurrently, at least one write, with no enforced ordering — the final value depends on non-deterministic scheduling rather than program logic.

Atomic operation (atomicAdd)

A single action that's guaranteed to happen all at once, with no other worker able to interrupt it halfway through — like a bank teller who won't start your neighbor's transaction until yours is fully done.

A hardware-guaranteed indivisible read-modify-write instruction. Critically, it only makes that one operation indivisible — a multi-step formula built from several reads and writes around it is not automatically made safe just because one step inside it uses an atomic.

Synchronization barrier (cudaDeviceSynchronize())

A checkpoint where you make everyone wait until every worker has finished the current task, before anyone starts the next one.

A host-side (CPU-side) call that blocks until every kernel previously launched on the device has completed execution — the only reliable way to guarantee that every thread's writes are visible before a dependent kernel reads them.

Throughput / speedup

How much work gets done per second, and how many times faster that is than the slow way of doing it.

Speedup = Tbaseline / Taccelerated, measured here in wall-clock seconds per training epoch via CUDA event timers, compared against a serial CPU implementation of the identical algorithm.

Slide 02 / 12

The problem

≈ 1:05
What's on the slide

One headline sentence, large: "Parallelizing training is easy. Parallelizing the optimizer is not." Below it, a simple two-part visual you sketch yourself (no figure in the paper covers this) — on the left, many small boxes labeled "Thread 1, Thread 2, … Thread 2048," each with an arrow pointing at one shared box on the right labeled "v (velocity)". That's the whole slide.

Say this, word for word
Let's start with why this problem exists at all. When you train a neural network on a GPU, you split your mini-batch across thousands of GPU threads — think of a thread as one tiny independent worker, and a kernel as the small program every worker runs at the same time. Each thread takes one training image, runs it forward through the network, and computes how wrong the prediction was. That part is what we call "embarrassingly parallel" — every thread's work is completely independent, so running two thousand of them at once is completely safe. But then comes the optimizer step — the part that actually updates the network's weights using that error signal. And optimizers like Momentum and Adam are not stateless. They keep a running memory — velocity for Momentum, moment estimates for Adam — that carries over from one training step to the next. All two thousand threads want to update that same shared memory at the same time. And that's where things quietly go wrong.
Why this slide exists

Every good conference talk earns its solution by first making the audience feel the problem. This slide plants the one idea the rest of the talk depends on: some parts of training are safe to parallelize, some aren't, and the difference is whether there's shared, persistent state.

Likely questions

What is a race condition, in one sentence?

It's when two or more threads read and write the same memory at the same time without coordination, so the result depends on unpredictable timing rather than the intended computation — and one thread's contribution can be silently erased by another's.

Isn't this just a threading problem that exists on CPUs too?

The underlying hazard is the same concurrency problem you'd see on a multi-core CPU — but the scale is different by orders of magnitude. A CPU might have 16 threads racing; here we have 2,048, and the GPU offers no cross-block synchronization primitive mid-kernel, so the exposure is both bigger and harder to guard against.

Mistakes to avoid
  • Don't say the phrase "race condition" before you've explained what it means — you'll lose anyone who isn't already a systems person.
  • Don't dive into CUDA syntax here. This slide is conceptual; save every piece of code for Slide 5.
  • Don't rush — this is the idea the entire talk is built on. If the audience doesn't get this slide, nothing after it lands.
Slide 03 / 12

Related work

≈ 0:50
What's on the slide

A short list, four lines max: Wang et al. — 17× inference speedup. Rao et al. — 487× backprop speedup. Zhao et al. — 110× speedup, 97.2% MNIST accuracy. Under the list, one bolded closing line: "None of these identify or resolve race conditions in stateful optimizers."

Say this, word for word
This isn't the first paper to accelerate neural network training with hand-written CUDA kernels. Wang et al. reported a 17× inference speedup, Rao et al. 487× for backpropagation, Zhao et al. 110× with 97.2% MNIST accuracy — genuinely impressive engineering. But every one of these only parallelizes the stateless parts: the forward pass, the backward pass, plain gradient descent. None of them puts a stateful optimizer like Adam inside a per-sample GPU kernel, so this particular race condition never had a chance to surface in their designs. Frameworks like PyTorch avoid the problem by construction — the optimizer step is always a separate function call from the backward pass — which means nobody using a framework ever sees why the naive version would be wrong in the first place.
Why this slide exists

A conference reviewer's first instinct is "hasn't someone already done this?" This slide answers that question before anyone has to ask it, and positions your contribution precisely: not faster kernels, but a correctness argument nobody else made explicit.

Likely questions

How is this different from just calling optimizer.step() separately in PyTorch?

Conceptually it's the same shape — separate the gradient phase from the state-update phase. Our contribution is making that separation explicit, naming the failure mode it prevents, and demonstrating with real accuracy numbers exactly what breaks if you skip it. Framework users get this for free and never see why it matters; we make the mechanism and its necessity visible.

What about asynchronous / distributed training work, like Dean et al.'s DistBelief?

Those systems sidestep the correctness question rather than answering it — they tolerate "stale" gradients, where a worker updates against slightly out-of-date weights. Our approach is fully synchronous and zero-staleness: every update uses the complete, current batch gradient, with no approximation.

Slide 05 / 12

The race condition

≈ 1:25
What's on the slide

The naive Momentum update equation (paper's Eq. 4), rendered large: v_t = βv_t + ∇W L. Below it, the tiny code snippet at right. In the corner, a callout box: "Momentum accuracy: 97.2% → 0.0%."

Say this, word for word
Now here's the actual bug. Imagine we write the Momentum update exactly the way the math tells us to, but inside a kernel where every one of 2,048 threads — one per training sample — runs this same line at once. Thread i reads the shared velocity value, computes its own updated version using its own gradient, and writes it back. Thread j does the exact same thing, at almost the same instant, using the same old velocity value it read a moment ago. Whichever thread writes last simply overwrites the other — not delays it, erases it. There's no error message, no crash, no compiler warning. The code runs, the network trains, the loss even looks like it's moving at first. But the optimizer's memory has been silently corrupted on every one of roughly eighteen thousand weights, every single batch. And the empirical result is not subtle: Momentum's accuracy collapses from 97.2 percent to 0.0 percent — indistinguishable from a network that was never trained at all.
Why this slide exists

This is the emotional and intellectual center of the talk — the "wait, that's a real bug" moment. Everything before this slide was setup; everything after it is resolution. Give it the time it needs and let the "0.0%" land with a pause before you move on.

Likely questions

Why doesn't atomicAdd already fix this?

atomicAdd only makes the addition itself indivisible — it guarantees no other thread interrupts that one add. But the Momentum formula is "read the old velocity, multiply by beta, add the gradient, write back" — several steps. An atomic protects one step, not the whole sequence, so the read and the write can still be split apart by another thread's operation in between.

Does this affect Adam too, or just Momentum?

Any optimizer with persistent, cross-step state is affected — Momentum's velocity, Adam's first and second moment estimates, RMSProp, LAMB. Plain SGD has no such state, so it's the one exception, which is actually part of why the bug is easy to miss: if you test SGD first, everything looks correct.

How did you first notice something was wrong?

The signature was unmistakable: Momentum and Adam collapsed to exactly the accuracy of random guessing on a 10-class problem — about 10 percent, or in some runs even lower — while the loss curve and code both looked superficially normal. That specific failure mode pointed straight at optimizer-state corruption rather than a hyperparameter or data issue.

Mistakes to avoid
  • Don't show messy real source code here — three lines of clean pseudocode teaches the bug faster than forty lines of your actual kernel.
  • Don't call it "just a bug" — frame it as a subtle, load-bearing correctness issue that compiles clean and produces no error, which is precisely what makes it dangerous.
  • Don't explain CUDA's hardware-level atomic implementation in depth here — that's a rabbit hole this audience doesn't need; keep the focus on the read/write ordering problem.
Slide 06 / 12

The fix: Two-Phase Gradient Accumulation

≈ 1:35
What's on the slide

A simplified version of Algorithm 1 — two labeled boxes, "Phase 1" and "Phase 2," with the code snippet underneath each. Name the technique in large text at the top: "Two-Phase Gradient Accumulation (2PGA)."

Say this, word for word
Our fix doesn't add locks, doesn't add warp-level tricks, and doesn't tolerate stale data. It changes who owns what memory, at two different points in the batch. In Phase 1, every thread still runs in parallel, but the only thing it's allowed to do to shared memory is add a number to it, using CUDA's atomicAdd — which is genuinely safe here, because addition is commutative: it doesn't matter what order two thousand additions happen in, the sum comes out the same either way. Once every thread has finished — enforced by a single hardware synchronization barrier — we launch a second kernel. But this time, instead of one thread per training sample, we launch one thread per weight. Thread k touches weight k, and nothing else. Nobody else is racing it. So the full Momentum or Adam formula — the one with the read, the multiply, the write — runs exactly once, by exactly one owner, with zero concurrent writers. No atomics are even needed in this phase, because there's no race left to arbitrate. And I want to stress this: this is not slower mini-batch SGD in disguise. Phase 1 already produced the correct summed gradient before our fix and after it — nothing changes there. The entire fix lives in Phase 2 alone.
Why this slide exists

This is the paper's central contribution — give it the most rhetorical weight in the whole talk. The goal is for one phrase to survive in the audience's memory after the talk ends: "Two-Phase Gradient Accumulation — many writers for the sum, one owner for the state."

Likely questions

Doesn't the synchronization barrier cost you performance?

Measurably, but small. For our 128×128 network, Phase 2 touches about 18,000 weights and finishes in under 0.01 milliseconds — under half a percent of one epoch's time. And the argument scales: however many parameters you have, you assign one thread per weight across enough blocks; "one owner per address" stays true no matter the parameter count, which is why we frame this as compatible with much larger, Transformer-scale models.

Does this generalize beyond Momentum and Adam?

Yes — the decomposition doesn't depend on the specific update formula. It depends only on separating what's commutative (gradient summation) from what isn't (a stateful recurrence). Any optimizer with cross-step state — RMSProp, LAMB, Adagrad — has the identical failure mode and the identical fix.

Why not just use a mutex or lock instead?

Locks would serialize access to shared state, but at massive throughput cost — thousands of threads contending for the same lock on the same address is a severe bottleneck on a GPU. 2PGA gets the same correctness with no locking at all, because Phase 2 removes the contention structurally rather than arbitrating it.

Mistakes to avoid
  • Don't undersell this as "we just moved some code around" — the insight is realizing which operations commute and which don't, and restructuring thread ownership around that distinction.
  • Don't forget to actually say the name "Two-Phase Gradient Accumulation" out loud, clearly, at least once — it's the one term you want people repeating back to you afterward.
  • Don't let this slide run past 100 seconds even though it's the most important one — a long, meandering explanation of your best idea is worse than a tight one.
Slide 07 / 12

Correct batch normalization on GPU

≈ 0:55
What's on the slide

The BN equations (paper Eq. 2–3) at the top, small. Below, a simple five-box pipeline diagram you draw yourself: linear → sync → stats → normalize → activate, each box connected by an arrow, with the sync step visually distinct (e.g. a vertical bar or gate icon) from the rest.

Say this, word for word
Batch normalization adds one more correctness wrinkle. To normalize a neuron's values, you need the mean and variance of that neuron across the entire batch — which means every one of 2,048 samples' values has to already be written to memory before anyone can safely read them to compute a mean. A single, one-shot kernel launch can't guarantee that, because different thread blocks run in an undefined order relative to each other, with no built-in way to signal "everyone's done." So we broke the batch-norm forward pass into a short pipeline of small kernels — compute the linear layer, synchronize, compute the batch statistics with a parallel reduction, apply the normalization, then activate — and mirrored the same structure going backward. Each synchronization point in between guarantees every sample's contribution is visible before the next kernel reads it.
Why this slide exists

It's the paper's second contribution, and it reuses the exact same "you need a barrier before anyone reads shared results" logic from Slide 6 — which makes it feel like reinforcement rather than a brand-new idea, and keeps this slide brisk.

Likely questions

Why not just synchronize once at the very end instead of once per layer?

Because each hidden layer's batch statistics depend on that layer's own linear output, which depends on the previous layer already being fully normalized and activated. The dependency chain is layer by layer, so the barrier has to be too — one synchronization at the end would let later layers read incomplete earlier results.

Does this add much overhead compared to training without batch norm?

Yes, measurably — our BN configurations run about 25–30% slower per epoch than the equivalent non-BN configuration, from the extra kernel launches and synchronization points. We see that as future kernel-fusion work rather than a flaw in the correctness argument itself.

  • Don't let this slide compete with Slide 6 for the audience's attention — keep it short and clearly secondary in the talk's structure.
  • Don't derive the batch-norm backward-pass math on the slide — name that it exists (the closed-form Ioffe–Szegedy identity) without deriving it live.

Slide 11 / 12

The BN+Adam anomaly — an honest limitation

≈ 0:55
What's on the slide

Figure 5 (BN impact bar chart), plus one annotated line under it: "Peaks 88.1% at epoch 2 → declines to 81.0% by epoch 20."

Say this, word for word
I want to spend one slide being upfront about a result that didn't go the way we expected. When we combine batch normalization with Adam and a learning-rate schedule, accuracy actually peaks early — 88.1 percent at epoch 2 — and then steadily declines to 81 percent by epoch 20. That's not slow convergence, that's instability: something is actively getting worse over training, not just improving slowly. We checked whether the learning-rate schedule itself was the cause by switching from a per-epoch to a per-batch cosine decay, and that only recovered about one point — so the schedule isn't the main culprit. Our leading hypothesis is a genuine interaction between Adam's evolving moment estimates and batch normalization's own evolving statistics — two different kinds of memory that may be working against each other during training. We think a batch-norm-aware optimizer, with decoupled learning rates for the normalization parameters, is the right next step, and we've left it as future work rather than smoothing it over.
