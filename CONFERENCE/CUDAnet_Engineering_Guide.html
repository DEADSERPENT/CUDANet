CUDAnet, completely explained

Every kernel, every optimizer, every race condition, and every place the shipped code quietly diverges from the paper that describes it — read end to end or jump to any of the 33 sections.

src/mnist_nn_cuda.cu · 2317 LoC RTX A2000 · sm_86 CUDA 12.0 · g++-12 784→128→128→10 MLP SGD · Momentum · Adam
Section 01

Project overview

CUDAnet is a multi-layer perceptron (MLP) trainer written directly in CUDA C — no PyTorch, no TensorFlow, no cuDNN, no cuBLAS. Every operation a deep learning framework normally hides behind a library call — matrix multiplication, ReLU, softmax, cross-entropy, batch normalization, SGD, Momentum, Adam, learning-rate scheduling — is a hand-written __global__ or __device__ function in a single 2,317-line source file, src/mnist_nn_cuda.cu. It trains and evaluates on MNIST (and Fashion-MNIST, via a compile-time flag), and the resulting binary is a few megabytes with a single runtime dependency: libcuda.so.

The repository builds fourteen variants of essentially one program, each a different compile-time configuration: cuda (SGD), cuda_momentum, cuda_adam, cuda_adam_lr (Adam + cosine LR schedule), cuda_batchnorm, cuda_full (BN + Adam + LR — the flagship configuration), cuda_wmma (Tensor Core variant), an OpenMP CPU baseline (serial_omp), a single-threaded CPU baseline (serial), and a standalone inference binary (infer). All fourteen compile from the same three source files via C preprocessor flags set on the nvcc command line in the Makefile — there is no branching source tree, only branching #if blocks.

Beginner framing

Think of a deep learning framework as a fully-furnished kitchen: PyTorch hands you a food processor (cuDNN), a stand mixer (cuBLAS), and pre-measured ingredients. CUDAnet is the same recipe cooked with a knife and a pan you forged yourself — slower to build, but you understand every step, and the finished kitchen fits in a shirt pocket (the binary is under 2 MB, versus PyTorch's multi-gigabyte install).

CUDA perspective

The project's real subject is not "can an MLP learn MNIST" — that has been true since the 1990s. It is a systems paper wearing an ML benchmark as a wrapper: the actual contribution is a concurrency pattern (Two-Phase Gradient Accumulation, §17) for correctly parallelizing stateful optimizers on a GPU, something that framework users never have to think about because cuDNN/cuBLAS already solved it for them, invisibly.

Section 02

Problem statement

When you parallelize neural network training across GPU threads — one thread per training sample in a mini-batch — the forward pass and the gradient computation are embarrassingly parallel: sample i's computation never touches sample j's intermediate values. But the parameter update is not embarrassingly parallel, because every sample in the batch wants to update the same shared weights. For plain SGD this is harmless — summing gradients is commutative, so it doesn't matter which thread's atomicAdd lands first. For Momentum and Adam, the update rule is stateful and nonlinear: it needs the previous velocity or moment estimate to compute the next one. Read-modify-write races on that shared state are not a performance nuisance — they are a correctness catastrophe.

Verified in this repository

This is not hypothetical. The results in results/ and the IEEE paper document exactly this failure: a naïve per-sample Momentum or Adam update collapses accuracy from 97.2% to 0.0% — indistinguishable from an untrained network. The network doesn't train slower; it doesn't train at all, and the code gives no compiler error, no CUDA error, and no crash. It just silently produces garbage.

Mathematical framing

Momentum's update is v ← βv + g, then θ ← θ − ηv. If two threads both read the same v, compute two different g-dependent successors, and write them back without ordering, the second write wins and the first thread's gradient contribution is silently discarded — not merely delayed, permanently lost. Do this for every one of 2048 threads on every one of ~18,000 weights, every mini-batch, for 20 epochs, and the velocity buffer never converges to anything meaningful.

Section 03

Why this problem exists

The bug exists because CUDA gives you exactly one cheap, hardware-guaranteed atomic primitive — atomicAdd — and it is easy to mistake "atomic add" for "atomic read-modify-write of an arbitrary formula." atomicAdd(&v, x) guarantees that the addition itself is indivisible: no other thread can interleave between the read and the write of that one operation. It says nothing about a sequence like "read v, multiply by β, add g, write back" — that sequence has a read step and a write step that are not fused into one hardware instruction, so any number of other threads can sneak in between them.

The failure mode is invisible for three compounding reasons: (1) the kernel compiles and runs without any CUDA error — races don't trigger exceptions; (2) SGD, which has no persistent optimizer state, is completely unaffected by the same code pattern, so a developer who tests SGD first sees correct behavior and reasonably assumes the parallelization strategy is sound; (3) the corruption is deterministic given a fixed thread-scheduling order but looks like divergence or random noise across runs, which developers often first blame on the learning rate, initialization, or a data bug rather than on the synchronization model.

CUDA perspective

This is a structural property of the SIMT execution model, not a coding mistake in the small. Warps within a block can be made to cooperate via __syncthreads(), but there is no such primitive across blocks within a single kernel launch — and with B = 2048 samples at 128 threads/block, this kernel spans 16 blocks that the scheduler may run in any order, on any SM, overlapping arbitrarily. Nothing short of ending the kernel (or, on newer architectures, cooperative-groups grid sync) provides a whole-grid barrier.

Section 04

Existing solutions

Three families of prior approach exist, and the paper's related-work section (§II) samples all three:

  • Framework-level solutions (PyTorch/cuDNN/cuBLAS). The optimizer step runs as a separate, dense kernel over the parameter tensor after gradients are already fully reduced — exactly the two-phase shape CUDAnet re-derives by hand, except the user never sees the seam.
  • Asynchronous/stale-gradient systems (Dean et al.'s DistBelief-style parameter servers). These sidestep the race by tolerating staleness — a worker may update against an out-of-date parameter snapshot — rather than eliminating it. Correct, but not synchronous, and not zero-staleness.
  • Kernel-tuning and throughput papers (Wang et al., Rao et al., Zhao et al., cited in the paper) report large inference/training speedups from manual CUDA kernels but parallelize only the stateless forward/backward math — none of them run a stateful optimizer per-sample inside a kernel, so the race this paper identifies never surfaces in their designs.
Beginner framing

PyTorch already "solves" this problem, but by construction, not by explicit design discussion: optimizer.step() is always a separate call from loss.backward(), and that separation alone prevents the race. Framework users never have the option to write the buggy version, so the failure mode this paper documents is invisible to almost everyone who has only ever trained models through a framework.

Section 05

Limitations of existing solutions

  • Frameworks hide the mechanism. They give you correctness but not the vocabulary to reason about why a naïve implementation would be wrong, which is precisely the knowledge gap this paper's "recovery" experiment (0% → 97.2%) is designed to make visible.
  • Frameworks are heavy. PyTorch's runtime is roughly 900× the on-disk size of CUDAnet's binary and needs a Python interpreter, libtorch, and CUDA libraries — impractical on a Jetson Nano-class or federated-learning edge device with a constrained RAM/storage budget (§33, §III of the paper).
  • Asynchronous/stale-gradient systems trade correctness for throughput; they don't answer whether a fully synchronous, zero-staleness parallel optimizer update is possible without locks — which is exactly the question Two-Phase Gradient Accumulation answers (§17).
  • None of the surveyed prior kernel-tuning work (§II of the paper) explicitly names cross-thread optimizer-state collision as a distinct correctness class, separate from ordinary numerical/floating-point non-determinism — so there is no existing "known fix" to borrow from that literature.
Section 06

The proposed solution

CUDAnet's answer is Two-Phase Gradient Accumulation (2PGA): split every mini-batch update into two serialized kernel phases with a hard synchronization point between them.

Phase 1
All B sample-threads run forward + backward in parallel and atomically accumulate raw gradients into a shared buffer. No optimizer state is touched — this phase is pure, commutative summation, which is the one thing atomicAdd is actually good for.
Barrier
cudaDeviceSynchronize() — the entire batch's gradient accumulation must be finished before anyone reads it.
Phase 2
A second kernel launches with exactly one thread per parameter (not per sample). Each thread owns exactly one weight or bias, reads the fully-accumulated gradient, divides by the batch size, and runs the full nonlinear Momentum/Adam recurrence — alone, with no other thread able to touch that address. No atomics are needed here because there is no concurrency to arbitrate.

This is implemented concretely as two kernels: one_learning_cycle (or, in the batch-norm build, a chain of per-layer kernels) for Phase 1, and apply_optimizer_update for Phase 2. See §17 for the full mechanism and §10 for kernel-by-kernel detail.

Technical framing

The insight generalizes past this codebase: any optimizer with cross-iteration state — Momentum, Adam, RMSProp, LAMB, Adagrad — has this same failure mode under naïve one-thread-per-sample parallelization, and the same two-phase decomposition fixes all of them, because the decomposition doesn't depend on the specific update formula; it depends only on separating "things that commute" (gradient summation) from "things that don't" (state recurrence).

Section 07

Complete architecture explanation

The default, paper-reported network is 784 → 128 → 128 → 10: a flattened 28×28 grayscale MNIST image, two hidden layers of 128 ReLU neurons, and a 10-way softmax output. The layer count and width are both runtime arguments (nl, nh), not compile-time constants, so the same binary can be re-run at 4×512 or any other shape up to 20 hidden layers.

Parameter layout

Every weight, bias, activation, pre-activation, and delta lives in one contiguous flat array — never an array-of-pointers, never a jagged structure. A single struct network_structure (defined identically, field-for-field, in mnist_nn_cuda.cu and infer.cu) precomputes four offset tables on the host once, before training starts:

FieldPurposeRecurrence
layers[i]neuron count of layer ilayers[0]=784, layers[L−1]=10
weights_pstn[i]flat offset of layer i's weight blockpstn[i+1] = pstn[i] + layers[i]·layers[i+1]
biases_pstn[i]flat offset of layer i's bias blockpstn[i+1] = pstn[i] + layers[i+1]
dza_pstn[i]per-sample offset for that layer's activation / z / delta slotpstn[i+1] = pstn[i] + layers[i]

Every weight index resolves in O(1): weights[weights_pstn[l] + i + j·layers[l+1]] connects input neuron j of layer l to output neuron i of layer l+1 — no pointer chasing, no indirection, a single multiply-add resolves any parameter's address from layer index alone.

Beginner framing

Instead of a weight matrix per layer (the natural object-oriented design — a Layer class holding its own 2-D array), everything is squeezed into one giant 1-D array, like packing every room of a house's furniture into a single shipping container with a manifest telling you exactly which byte offset each item starts at. It's less readable at a glance but far friendlier to a GPU, which prefers flat, contiguous, predictable memory.

CUDA perspective

Flat layout means the entire network_structure struct (arrays of 22 ints, twice over for weights/biases/dza plus BN offsets) can be passed by value into every kernel launch — it is small enough (well under 1 KB) to sit in constant/parameter space rather than requiring a separate device allocation and pointer dereference per kernel, which would otherwise cost an extra global-memory round trip on every single kernel invocation.

Section 08

CUDA execution flow

One training step (one mini-batch) takes one of three shapes depending on compile-time flags — the same source tree branches three ways at #if USE_BATCH_NORM / #elif USE_TENSOR_CORES / #else inside main().

BuildPath takenKernel count / step
cuda, cuda_adam, cuda_adam_lr…monolithic one_learning_cycle + Phase 22 launches
cuda_batchnorm, cuda_fullper-layer staged pipeline (§10, §18)~10–14 launches / layer-pass
cuda_wmmabatched WMMA GEMM per layer effectively dead — see §Avaries

The non-BN path (the one actually used for the paper's SGD/Momentum/Adam/Adam+LR numbers) is:

// once per mini-batch, nb = 2048 samples
one_learning_cycle<<<16, 128>>>(...);      // Phase 1: forward+backward+atomicAdd gradient accum
cudaDeviceSynchronize();
apply_optimizer_update<<<opt_blocks, 256>>>(...); // Phase 2: one thread per weight, no atomics

The BN path replaces that single Phase-1 kernel with an explicit per-layer forward chain (init → linear → stats → apply → activation) and a mirrored per-layer backward chain, each pair of stages separated by a synchronization point, because batch statistics genuinely need every sample's value before anyone can consume them (§18, §19).

Section 09

Memory flow

Data crosses the host↔device boundary exactly once per run for the large, static tensors, and never again during training:

  1. Load — load_mnist() reads the four IDX-format binary files (§ GPU memory layout) into pinned host arrays via raw read() syscalls, converts uint8 → float32 and normalizes to [0,1].
  2. Upload — one cudaMemcpy(..., cudaMemcpyHostToDevice) each for the full 60,000-image training set (~180 MB) and 10,000-image test set (~31 MB), plus weights, biases, and every optimizer-state buffer. This happens once, before the epoch loop.
  3. Per mini-batch — only a tiny array of nb random sample indices (batch_d, 2048 ints = 8 KB) is copied host→device each step; the images themselves are never re-copied; kernels index directly into the already-resident train_image_d array.
  4. Per epoch — a handful of scalar accuracy numbers copy device→host so printf can report progress; everything else stays resident on the GPU for the entire run.
  5. End of run — weights/biases copy back to host once (if save_flag is set) and every device buffer is freed.
Technical framing

This is the single biggest structural reason CUDAnet's GPU numbers look so favorable next to the CPU baseline (§28): the CPU baseline reads the same 180 MB dataset from host RAM on every single epoch's pass over the data, while the GPU version pays that transfer cost exactly once for the whole run and then operates entirely out of VRAM. It is a legitimate architectural advantage, not an accounting trick — but it does mean the reported speedup partly reflects "data locality" as much as "compute throughput" (see the audit note on the CPU baseline in §28 and §A).

10.1 — The evaluation-kernel stack overflow fix

An early version of evaluate_kernel declared float z[1024]; float a[1024]; as ordinary local arrays. Ordinary local arrays that exceed the register budget spill to local memory, which is per-thread private but physically backed by the same off-chip DRAM as global memory — and it is allocated per thread. At 10,000 test images run concurrently and 1024 floats × 4 bytes × 2 arrays, that is roughly 80 MB of local-memory pressure, which blew the CUDA context. The fix (present in the current code) allocates global_a/ global_z once in genuine global VRAM before the kernel launch and passes per-thread pointers in: float* a = &global_a[id * ns.num_nodes];

CUDA perspective

This is a textbook illustration of the difference between "large automatic array" and "large allocation": the fix doesn't reduce total memory used (global VRAM is exactly as physically far away as spilled local memory) — it reduces per-launch allocation pressure by making the buffer explicit and shared-address-space rather than an implicit per-thread stack frame the compiler has to reserve for every one of 10,000 threads regardless of occupancy.

Discrepancy — dead Tensor Core kernels

wmma_fwd_kernel and wmma_bwd_delta_kernel (lines 988–1116) are genuine, correct Tensor Core kernels — real wmma::fragment/wmma::mma_sync calls on 16×16×16 tiles, not a scalar approximation. But they never actually run in any binary the Makefile builds. See §A for the root cause (an unguarded preprocessor #define silently resets USE_TENSOR_CORES back to 0 regardless of the -D flag passed at compile time) — verified by preprocessing the exact cuda_wmma flags and finding zero occurrences of either kernel name in the output.

Section 12

How SGD works here

Beginner framing

SGD nudges every weight a small step in the direction that would have made the last batch's predictions less wrong. No memory of previous steps — every update starts fresh from the current gradient alone.

θₜ₊₁ = θₜ − η·∇W L paper Eq. — SGD
Technical framing

In sgd_layer_update_kernel, each of the 2048 sample-threads independently computes its own contribution to ∇W L for a layer, and applies it immediately and directly to the shared weight via atomicAdd(&weights[idx], -alpha_nb * d[i] * a[j]) — no separate Phase 2 kernel is needed for SGD, because there is no persistent state for a race to corrupt. alpha_nb = learning_rate / batch_size is precomputed once per step so the average-over-batch division is folded into every atomic add rather than done afterward.

CUDA perspective

This is the one case in the whole codebase where 2048 threads genuinely do race on the same memory address — and it is completely safe, because floating-point addition is commutative and atomicAdd serializes the individual adds at the hardware level. Order doesn't matter when the operation being repeated is "+=".

Section 13

How Momentum works here

Beginner framing

Momentum adds inertia: instead of reacting only to this batch's gradient, it keeps a running "velocity" that accumulates a fraction of every previous gradient, so training rolls through small bumps in the loss surface rather than stopping at every one of them — the same intuition as a ball rolling downhill picking up speed.

vₜ = βvₜ₋₁ + (1−β)∇W Lₜ    θₜ₊₁ = θₜ − ηvₜ β = 0.9
Mathematical framing

The code implements this as an equivalent single-step delta, v ← v + [(1−β)(g − v)], algebraically identical to v ← βv + (1−β)g but written as one additive correction — which matters because it is the exact form that makes the naïve-but-broken per-sample atomicAdd version (§16) look deceptively safe at first glance.

Technical framing

In the shipped, correct build, Phase 1 (one_learning_cycle, OPTIMIZER_TYPE==1 branch) only ever calls atomicAdd(&grad_b[...], local_grad) — raw gradient summation, no v in sight. The actual momentum recurrence — v ← 0.9v + g_avg, θ ← θ − ηv — runs once per weight inside apply_optimizer_update's OPTIMIZER_TYPE==1 branch, with no atomics, because each of that kernel's threads owns exactly one weight index.

Section 14

How Adam works here

Beginner framing

Adam keeps two running estimates per weight — an average of recent gradients (like Momentum) and an average of recent squared gradients (a rough estimate of how noisy/large that weight's updates have been). It divides the step by the square root of the second estimate, so weights with consistently large gradients get smaller effective steps and weights with small, rare gradients get relatively larger ones — an adaptive, per-weight learning rate.

mₜ = β₁mₜ₋₁+(1−β₁)g   vₜ = β₂vₜ₋₁+(1−β₂)g²
m̂ = mₜ/(1−β₁ᵗ)   v̂ = vₜ/(1−β₂ᵗ)   θₜ₊₁ = θₜ − η·m̂/(√v̂+ε) β₁=.9 β₂=.999 ε=1e-8

This matches the paper's Eq. 9–12 exactly and matches apply_optimizer_update's OPTIMIZER_TYPE==2 branch term for term.

Discrepancy — the bias-correction step counter t

Canonical Adam increments t once per optimizer step (once per mini-batch). This code passes epoch + 1 as t into every call of apply_optimizer_update — and that call happens 23 times per epoch (once per mini-batch, in the paper's 48,000/2048 configuration), all sharing the same t value until the epoch counter itself advances. Concretely: across 20 epochs and 23 mini-batches each, canonical Adam would use t ∈ {1 … 460}; this implementation only ever uses t ∈ {1 … 20}.

Numerically this matters more for β₂ than β₁, because 1−β₂ᵗ grows far more slowly: at t=20, 1−0.999²⁰≈0.0198; at the canonical t=460 it would be 1−0.999⁴⁶⁰≈0.369. A smaller denominator inflates v̂, which shrinks the effective step (η·m̂/(√v̂+ε)) — so every mini-batch within an epoch is, relative to textbook Adam, running with a slightly more conservative effective learning rate than intended, an effect that only fades as the epoch (not the mini-batch) counter climbs. The paper does not mention this; it presents the standard equations without flagging the substitution.

CUDA perspective

This is entirely orthogonal to the race-condition story: it's a scalar bookkeeping choice (which counter to pass into a powf call), not a synchronization bug — every thread in Phase 2 still owns its own weight with no concurrency hazard. It's a legitimate, independent deviation from the reference algorithm worth knowing about if you're trying to reproduce the exact accuracy numbers with a from-scratch reimplementation.

Section 15

Why race conditions happen

Three properties have to hold simultaneously for a race to become a correctness bug rather than a curiosity, and CUDAnet's naïve (pre-fix) Momentum/Adam path hits all three:

  1. Shared mutable state. A memory address (one entry of the velocity or moment buffer) that more than one thread will write to in the same kernel launch.
  2. Non-commutative update. The new value depends on reading the old value through a nonlinear formula (βv+g, not simply v+g) — order of application changes the result.
  3. No enforced ordering. CUDA gives no guarantee about which thread, on which SM, executes first, last, or concurrently with any other — within one kernel launch, across blocks, there is no built-in barrier at all.
Mathematical framing

Sequential composition of the Momentum recurrence is well-defined: apply v←βv+g₁, then v←βv+g₂, and so on — order matters, and it's supposed to (that's what "momentum" means). Concurrent application without ordering isn't "a different but valid sequence" — it's an ill-defined operation: two threads computing βv₀+g₁ and βv₀+g₂ from the same stale v₀ and racing to write back means whichever writes last simply erases the other's gradient contribution. It is not equivalent to any valid ordering of the batch; it is strictly less information than either individual update.

Beginner framing

Imagine two people editing the same shared notebook total at the same time. Both read "current total: 100." Both add their own number and write back their new total. Whoever writes second overwrites the first person's update entirely — the notebook only reflects one person's contribution, not both. Now do that with 2,048 people and 18,000 notebooks, continuously, for twenty rounds. That's the failure mode.

Section 16

Exactly where the race would happen

The codebase keeps physical evidence of the exact buggy pattern: two __device__ functions, update_param_momentum and update_param_adam (lines 461–499), are defined but — verified by grep across the whole file — never called from anywhere. They are the fossil record of the naïve, race-prone design the paper describes fixing.

// lines 461–469 — defined, but dead: never invoked
__device__ void update_param_momentum(float* param, float grad, float* velocity, float lr, float momentum){
    // v = v + [(1-momentum)*(grad - v)]   — looks atomic-safe (one atomicAdd call)...
    atomicAdd(velocity, grad - (1.0f - momentum) * (*velocity));   // ...but *velocity was read moments earlier, non-atomically
    float v_val = *velocity;
    atomicAdd(param, -lr * v_val);
}

The single atomicAdd call is genuinely atomic as an addition — but the value being added, grad - (1.0f - momentum) * (*velocity), is computed from a plain, non-atomic dereference of *velocity taken just before the call. Between that read and the atomic write, any number of the other 2,047 threads may have already changed *velocity. The delta this thread adds is stale the moment it's computed. Summing 2,048 such staggered, stale deltas does not reproduce the sequential recurrence v = βv + g_avg — it reproduces something with no clean mathematical description, and empirically, garbage (0% accuracy per the paper's Table II).

CUDA perspective

Had this function instead been called once per weight — exactly what apply_optimizer_update actually does today — the same line of code would be completely correct, because there would be no concurrent reader/writer of *velocity to race against. The bug isn't in this function's arithmetic; it's entirely in the calling convention (one thread per sample instead of one thread per parameter). That distinction is the whole of Two-Phase Gradient Accumulation.

Section 17

How Two-Phase Gradient Accumulation solves it

2PGA doesn't add locks, warp-level primitives, or staleness tolerance. It removes the race by construction: it changes which thread owns which memory address, at two different points in the same batch's computation.

Phase 1 — many writers, one operation

2,048 threads, each one thread per sample. Every thread may write to any weight's gradient accumulator, but the only operation performed is atomicAdd — pure summation. Concurrent, commutative, safe.

Phase 2 — one writer per address

The grid is re-sized to one thread per parameter ( ⌈num_weights/256⌉ blocks of 256). Thread k touches weight k and nothing else. The full nonlinear recurrence runs exactly once, with zero concurrent readers or writers of that address — no atomics needed, because there is no race to arbitrate.

// Phase 1 (grad_accum_layer_kernel) — nb threads, safe because "+" commutes
atomicAdd(&grad_w[widx], d[i] * a[j]);

// barrier
cudaDeviceSynchronize();

// Phase 2 (apply_optimizer_update) — num_weights threads, one owner each
float grad = grad_w[idx] / (float)nb;              // average over batch
m_w[idx] = ADAM_BETA1*m_w[idx] + (1-ADAM_BETA1)*grad;
v_w[idx] = ADAM_BETA2*v_w[idx] + (1-ADAM_BETA2)*grad*grad;
float m_hat = m_w[idx] / (1 - powf(ADAM_BETA1, t));
float v_hat = v_w[idx] / (1 - powf(ADAM_BETA2, t));
weights[idx] -= lr * m_hat / (sqrtf(v_hat) + ADAM_EPSILON);
grad_w[idx] = 0.0f;                                    // reset accumulator for next batch

Note this is precisely not "mini-batch SGD renamed" — Phase 1 already produced the correct batch-summed gradient under ordinary accumulation; nothing about Phase 1 changes between the broken and fixed versions. The entire fix is confined to Phase 2: preventing state corruption by guaranteeing exactly one write per parameter per batch.

Mathematical framing

Cost analysis (paper §VIII-A): for the 128×128 network, Phase 2 touches ≈18,000 weights and finishes in under 0.01 ms — under 0.4% of a 20 epoch/23-batch epoch's total time. The argument scales without modification to arbitrarily many parameters: assign one thread (across as many blocks as needed) per weight, and "each weight has exactly one owner" remains true at any parameter count — the paper explicitly frames this as compatible with Transformer-scale models.

Section 18

Batch normalization implementation

Beginner framing

Batch normalization re-centers and re-scales every neuron's pre-activation values so they have roughly zero mean and unit variance across the current mini-batch, then lets the network learn its own preferred scale (γ) and shift (β) on top of that. It tends to make training more stable and less sensitive to initialization and learning rate.

μⱼ = (1/|B|)Σᵢz⁽ˡ⁾ᵢⱼ   σⱼ² = (1/|B|)Σᵢ(z⁽ˡ⁾ᵢⱼ−μⱼ)²
ẑᵢⱼ = (z⁽ˡ⁾ᵢⱼ−μⱼ)/√(σⱼ²+ε)   z̃ᵢⱼ = γⱼẑᵢⱼ+βⱼ

The GPU-specific difficulty (and the reason BN needs its own multi-kernel architecture, distinct from the monolithic path) is that μⱼ and σⱼ² are reductions over the batch dimension — computing them for neuron j requires every one of the 2,048 samples' z-values to already be written to memory. A single per-sample kernel launch (as used for the non-BN path) cannot guarantee that: a thread computing block 3's mean might start before block 12 has even begun its forward pass.

The fix is the staged pipeline already listed in §10: fwd_linear_kernel → (synchronize) → bn_stats_kernel (one CUDA block per neuron, a classic shared-memory tree reduction — sum, then sum-of-squared-deviations, each halving the active thread count every step) → bn_apply_kernel → apply_activation_kernel, repeated per hidden layer, then mirrored in the backward direction.

Backward pass — the closed-form shortcut

The backward pass uses the standard Ioffe & Szegedy closed-form BN-gradient identity, which needs exactly two batch-wide sufficient statistics — Σδ and Σ(δ·ẑ) — rather than the three-pass, per-element recomputation a naïve derivation would require:

∂L/∂z_pre[i] = (γ/(√(σ²+ε)·N))·(N·δᵢ − Σδ − ẑᵢ·Σ(δ·ẑ))
Discrepancy — a superseded BN code path still ships

An entirely separate, earlier implementation of batch norm exists in the file: batch_norm_forward, batch_norm_forward_sample, and batch_norm_backward (lines 502–646), plus the #if USE_BATCH_NORM block inside one_learning_cycle (lines ~1500–1671) that calls them. These implement BN with an O(batch²) redundant-recomputation strategy — every thread recomputes the full batch mean/variance itself rather than sharing one reduction — and are architecturally the exact race-prone shape the paper's §III-B calls out as incorrect (one unsynchronized kernel launch cannot see every sample's z before computing statistics from it). Verified from main(): when USE_BATCH_NORM=1, the training loop takes the #if USE_BATCH_NORM branch at the top level and calls the correct per-layer kernel chain — it never calls one_learning_cycle at all. This older implementation compiles, sits inert in every BN binary, and is never executed.

Section 19

Why cudaDeviceSynchronize() is required

Beginner framing

Launching a CUDA kernel is like dropping a letter in a mailbox and walking away — the CPU doesn't wait for the GPU to actually finish before moving on to the next line of code. cudaDeviceSynchronize() is the CPU explicitly waiting at the mailbox until it's confirmed empty: every bit of work queued on the device up to that point has genuinely completed.

Technical framing

Within one kernel launch there is no cross-block barrier at all — different thread blocks may run on different SMs, in any order, with any amount of overlap. Between fwd_linear_kernel (which writes every sample's z) and bn_stats_kernel (which reads every sample's z to compute a mean), that ordering guarantee has to come from somewhere — either an explicit host-side wait, or reliance on stream semantics.

A precise, non-obvious nuance

Grep confirms this codebase never calls cudaStreamCreate or uses any stream object anywhere — every kernel launches on the implicit default stream, and CUDA already guarantees that kernels issued to the same stream execute in program order, one fully finishing before the next begins. That guarantee alone would already be enough to make bn_stats_kernel safely see every write from the preceding fwd_linear_kernel, without an explicit cudaDeviceSynchronize() call — which is exactly why the (also correct) SGD update loop elsewhere in the file launches several sgd_layer_update_kernel calls back-to-back with no synchronize between them at all, and is still race-free. So the explicit barriers around the BN kernels are best understood as defensive, documentation-grade correctness — they make the dependency impossible to get wrong even if the code later grows explicit streams (the header already scaffolds unused USE_ASYNC_STREAMS/NUM_STREAMS constants for exactly that future), rather than being the only thing standing between this code and a race today. The paper's framing — "acting as an implicit global barrier" — is correct but slightly overstates how load-bearing the explicit call is in the current, single-stream build.

CUDA perspective

Where cudaDeviceSynchronize() is unambiguously load-bearing, regardless of stream semantics, is the boundary between Phase 1 and Phase 2 of 2PGA: Phase 2's entire correctness argument depends on Phase 1's grad_w/ grad_b accumulation being completely finished — every one of 2,048 threads' atomic adds landed — before Phase 2 reads it. Default-stream ordering already guarantees this between the two kernel launches, but the explicit call also gates the host-side epoch timer (cudaEventElapsedTime) and the periodic accuracy evaluation, which do need the device idle before they mean anything.

Section 20

The training loop

for epoch in 0..ne:
    lr = update_learning_rate(alpha, epoch, ne)        // step / exponential / cosine
    if epoch % log_interval == 0: evaluate + print train/val/test accuracy

    for b in 0..num_batches:                          // num_batches ≈ 23 for nb=2048, 48000 train
        sample nb random indices from the TRAINING portion only (never validation)
        upload batch_d (indices) to device
        zero gradient / BN-gradient accumulators

        Phase 1: one_learning_cycle  (or the staged BN pipeline)
        barrier: cudaDeviceSynchronize()
        Phase 2: apply_optimizer_update   (+ bn_params_update_kernel if BN)

    record elapsed time via CUDA events

Two details matter for reproducing the paper's numbers precisely: an 80/20 train/validation split is carved out of the 60,000 training images (USE_VALIDATION_SPLIT), leaving 48,000 for actual gradient steps and 12,000 held out purely for monitoring; and the inner for b in 0..num_batches loop means one "epoch" is a genuine full pass over the 48,000-sample training portion (⌊48000/2048⌋ = 23 mini-batches), not a single mini-batch as an earlier version of the code and, until it was corrected, the top-level README both described (§A).

Section 21

Forward propagation

z⁽ˡ⁾ = W⁽ˡ⁻¹⁾a⁽ˡ⁻¹⁾ + b⁽ˡ⁻¹⁾   a⁽ˡ⁾ = ReLU(z⁽ˡ⁾)   (l < L−1)  ·  a⁽ᴸ⁻¹⁾ = softmax(z⁽ᴸ⁻¹⁾)

The core matrix-vector product is weight_x_a, a plain double loop with four optimization tiers layered on top of it via compile-time flags: naive global-memory reads → shared-memory 32×32 cooperative tiling (weight_x_a_shared, the only tier actually enabled by default) → an FP16-with-FP32-accumulate scalar variant (weight_x_a_mixed, disabled — measured slower) → the true WMMA tile path (dead per §A). Softmax subtracts the row-max before exponentiating for numerical stability, a textbook safeguard against overflow for large logits.

CUDA perspective

The shared-memory tiling path only activates when both layer dimensions fit within TILE_SIZE=32 — true for every hidden layer at width 128? No: 128 > 32, so the shared-memory branch's l_num <= TILE_SIZE && l_next_num <= TILE_SIZE guard is false for the paper's actual 784→128→128→10 network, meaning every layer in the reported configuration silently falls through to the plain global-memory weight_x_a path inside weight_x_a_shared — the shared-memory optimization exists and is compiled in, but never actually engages at the network width the paper benchmarks.

Section 22

Backward propagation

δ⁽ᴸ⁻¹⁾ = â − y  (one-hot)  ·  δ⁽ˡ⁾ = (W⁽ˡ⁾)ᵀδ⁽ˡ⁺¹⁾ ⊙ ReLU′(z⁽ˡ⁾)

Cross-entropy loss paired with a softmax output layer has the famously clean gradient â−y — delta_cross_entropy computes exactly this, a single subtraction per output neuron, avoiding the chain rule through softmax's own Jacobian entirely. The optional Sigmoid+MSE output mode (output_type=0) instead needs the explicit product (â−y)·σ′(z), computed inline in one_learning_cycle. Hidden-layer deltas propagate backward one layer at a time via weight_x_d (the transpose-direction matrix-vector product), masked by the ReLU derivative — a hard 0/1 gate depending only on the sign of the forward-pass z, which is why z (not just a) has to be retained from the forward pass.

Section 23

Parameter updates

Weight and bias gradients themselves come from the same outer-product rule regardless of which optimizer eventually consumes them: ∂L/∂W⁽ˡ⁾ᵢⱼ = δ⁽ˡ⁺¹⁾ᵢ·a⁽ˡ⁾ⱼ, ∂L/∂b⁽ˡ⁾ᵢ = δ⁽ˡ⁺¹⁾ᵢ. What happens to that gradient next is entirely a function of OPTIMIZER_TYPE and is exactly the SGD/Momentum/Adam split already covered in §11–§14 and the 2PGA mechanism in §17 — this section exists mainly to name where in the pipeline that split occurs: immediately after backward propagation finishes computing every layer's δ, in the loop for l in 0..L-1: accumulate weight/bias gradients for layer l, inside Phase 1.

On-disk format (IDX, read by load_data.h)

MNIST's IDX format stores a big-endian 4-int header (magic, count, rows, cols for images; magic, count for labels) followed by raw uint8 pixel/label bytes. FlipLong byte-swaps that header on little-endian hosts; image_char2float then divides every pixel by 255 to normalize into [0,1] before the one-time upload to device.

Section 25

Thread hierarchy

Three distinct "one thread per X" conventions coexist in this codebase, and knowing which one a given kernel uses is the single fastest way to understand whether it's safe to use atomics or not:

GranularityUsed byConcurrent writers per address?
one thread / sampleone_learning_cycle, fwd_linear_kernel, backward_delta_kernel, grad_accum_layer_kernel, sgd_layer_update_kernelyes, on shared weight/bias entries — safe only for commutative ops (atomicAdd)
one thread / parameterapply_optimizer_update, bn_params_update_kernelno — this is precisely how 2PGA eliminates the race
one block / neuronbn_stats_kernel, bn_backward_stats_kernelno cross-block writers; within-block reduction uses __syncthreads(), not atomics

Within a block, a warp (32 threads) executes in lockstep; __syncthreads() is a block-wide barrier used inside the BN reduction kernels between each halving step of the tree-sum. __syncwarp() appears only inside the dead WMMA kernels (§A), guarding shared-memory staging within a single 32-thread warp before a tensor-core mma_sync.

Section 29

How to read the paper's graphs

  • Fig. 2 (accuracy curves, all six configs). Momentum and Adam converge above 96% within 5 epochs and plateau near 97.2%; BN+Adam+LR is the visibly anomalous curve — it peaks near epoch 2 (88.1%) and then declines monotonically for the remaining 18 epochs. A curve that rises then falls is a symptom of instability (something actively degrading the solution), not slow convergence (something that just hasn't finished improving yet) — the paper's own framing in §VII-D.
  • Fig. 3 (time/epoch, log scale + speedup bars). Log scale is necessary because the serial-CPU estimate (~2070 s) and the GPU times (~1 s) differ by three orders of magnitude; plotted linearly, every GPU bar would be visually indistinguishable from zero.
  • Fig. 4 (before/after 2PGA, grouped bars). The hatched red bars are the race-condition baseline; solid bars are post-fix. Reading this figure correctly requires remembering that SGD's bar moves too (74.9%→94.3%) for a reason unrelated to 2PGA — the full-dataset inner-loop change — while Momentum/Adam's near-total recovery (0%→97.2%) is 2PGA's actual effect.
  • Fig. 5 (BN impact, SGD vs Adam+LR). The point of this figure is the asymmetry: BN costs SGD almost nothing (−1.2 pp) but costs Adam+LR a great deal (−16.0 pp) — evidence that the interaction is specifically between BN's evolving statistics and Adam's moment estimates, not a generic "BN overhead" story.
Section 30

How to read the paper's tables

  • Table I is the only table with an estimated row (Serial CPU) mixed in with measured rows — the speedup multipliers in its rightmost column inherit that estimate's uncertainty (see §28's audit note).
  • Table II isolates the 2PGA effect specifically; its "Recovery" column is the headline number the entire paper is built around.
  • Table III is the one to cite for "final accuracy leaderboard" purposes — note BN+Adam+LR sits at the bottom despite being the most feature-complete configuration, which is the paper's central, slightly uncomfortable finding (more machinery ≠ better result here).
  • Table IV (epoch-by-epoch) is what actually substantiates "BN+Adam+LR is unstable, not slow" — you can see the peak-then-decline pattern in the raw numbers (83.7% → 82.1% → 81.4% → 81.0%), not just in the figure.
  • Table V (batch-size scaling) is measured in a different mode ("single-batch mode" per its own footnote) from every other table in the paper (which use the full-dataset inner loop) — its absolute epoch times are not directly comparable to Table I's.
  • Table VI (vs. PyTorch) is the edge-deployment argument in numbers: CUDAnet trades a 4× slower epoch and 0.7 pp lower accuracy for a 527× smaller VRAM footprint and 900× smaller install size — read it as a Pareto trade-off, not a "CUDAnet wins" claim.
Section 31

Contributions

  1. Two-Phase Gradient Accumulation — a general, lock-free, staleness-free pattern for parallelizing any stateful optimizer on a GPU by separating commutative gradient summation (many writers, one operation) from stateful update application (one writer per parameter).
  2. A correct, per-layer-staged CUDA implementation of Batch Normalization using cudaDeviceSynchronize() as an explicit dependency barrier between batch-statistics computation and its consumers.
  3. A from-scratch, dependency-free training engine under 2 MB, whose only runtime dependency is libcuda.so — a genuine edge/IoT deployment argument backed by a concrete PyTorch comparison (Table VI).
  4. An empirical, reproducible demonstration that the race condition is not theoretical: 0.0% accuracy is an unambiguous, easily-verified failure signature, and the before/after tables in this codebase's results/ directory back it with raw logs, not just summary numbers.
Section 32

Limitations

  • Accuracy ceiling. 97.2% trails CNN-based MNIST results (>99%) because an MLP has no translation-equivariant structure — a deliberate scope choice (isolate the parallel systems question from convolutional complexity), not an oversight, but it does mean the accuracy numbers alone aren't competitive with modern architectures.
  • BN+Adam+LR genuinely underperforms (81.0%, 16.2 pp below plain Adam), and the paper is candid that this isn't fully understood — the epoch-2 peak and subsequent decline are reproducible and don't resolve with LR-schedule fixes alone; the leading hypothesis (competing "moving targets" between Adam's moment estimates and BN's evolving batch statistics) remains a hypothesis, not a proven diagnosis.
  • The serial-CPU baseline is an estimate, not a completed measurement, so the headline ">2,000× speedup" should be read as an order-of-magnitude claim.
  • Phase-2 synchronization overhead grows with batch size — roughly 17% more epoch time at batch 4096 vs. 2048 — meaning 2PGA's near-zero-cost claim is a property of the tested batch-size regime, not unconditionally true at arbitrary scale.
  • Engineering debt not mentioned in the paper: the dead Tensor Core path (§A) and the superseded in-kernel BN implementation (§18) are real gaps between "what the repository contains" and "what the paper describes," documented in full in the appendix below. (A third gap, a stale README accuracy table, was found during this audit and has since been corrected.)
Section 33

Future work

  • Actually wire up the Tensor Core path. The true WMMA kernels (wmma_fwd_kernel, wmma_bwd_delta_kernel) already exist and are architecturally sound (real mma_sync on 16×16×16 tiles, and 784/128/2048 are all multiples of 16, so the default network shape is actually eligible) — the paper lists WMMA integration as future work, but the bulk of the implementation is already written and only needs the preprocessor guard fixed (§A) plus a genuine benchmark run to validate the paper's own 2–3× throughput projection.
  • Convolutional layers via im2col + GEMM, to move past MNIST toward CIFAR-10, as the paper proposes.
  • Multi-GPU scaling via NCCL AllReduce on Phase 1's already-accumulated gradients — a natural extension the paper notes requires no change to the core 2PGA correctness argument, since Phase 1 output (a summed gradient) is exactly what AllReduce also produces across devices.
  • A decoupled or BN-aware Adam variant, to address the BN+Adam+LR instability directly rather than working around it with LR-schedule tuning alone.
  • Housekeeping: guard USE_TENSOR_CORES/ USE_MIXED_PRECISION with #ifndef the way OPTIMIZER_TYPE and USE_BATCH_NORM already are; delete or clearly mark as historical the dead update_param_momentum/ update_param_adam functions and the superseded in-kernel BN path. (README.md's accuracy table has already been refreshed to match results/ and the paper.)

Net assessment

The paper's central, load-bearing claim — that naïve per-sample stateful-optimizer parallelization races and silently corrupts training, and that a two-phase accumulate/apply split fixes it with negligible overhead — is fully substantiated by the shipped code, down to vestigial dead functions that are the fossil record of the "before" state. The gaps found above are all in secondary claims (WMMA status, BN implementation cleanliness, VRAM accounting, one optimizer bookkeeping detail) and do not weaken the core contribution; they are exactly the kind of detail a rigorous reviewer — or a co-author preparing slides — should know about before presenting the numbers. Two items surfaced by this audit (the stale README table, and the serial-CPU baseline actually having a completed measurement on hand) have already been resolved.
